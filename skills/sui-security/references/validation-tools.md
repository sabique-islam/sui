# Security validation and fuzzing tools

Use only targets and environments the task actually authorizes. Scanning, fuzzing and penetration testing complement review and tests; none certifies absence of vulnerabilities.

## Bounded penetration-test method

Define asset/target allowlist, owner/permission, white/gray/black-box knowledge, excluded systems/actions, time/rate/data limits, contacts, stop criteria, evidence handling and retest. Use a disposable lab for examples. Move from permitted reconnaissance to service discovery, vulnerability assessment, carefully scoped confirmation and an impact/remediation report. Exploitation is a separately consequential action; do not execute it merely because the lifecycle lists a phase. Preserve the chain from observed service/input/control failure to reproducible impact, false-positive review, proposed fix and verification.

WHOIS supplies registration/context, not owner identity certainty or permission to test. Shodan supplies indexed observations that may be stale or shared-host ambiguities; map an authorized target and timestamp before use and do not expand scope from search results. Inspect official response schemas/account limits before adding a read-only connector. Public data is still untrusted and may contain personal information.

Nmap: choose authorized hosts/ports/probe/rate and preserve complete XML plus timing/version; the local XML parser requires a successful completion marker and treats open ports as observations rather than proven vulnerabilities. Official: https://nmap.org/book/output-formats-xml-output.html .

ZAP/OWASP ZAP: define a scoped context, authentication/session handling and excluded paths; distinguish passive observation from active scanning. Preserve the version's JSON/SARIF report, run status and target identity; the JSON adapter requires sites and retains alert risk/rule identity. Official: https://www.zaproxy.org/docs/ .

Metasploit: select a specifically authorized lab/module, read preconditions/side effects and target compatibility, preserve session/cleanup and report only observed bounded impact. No automatic exploit module runs are bundled. SQLMap: identify the specifically authorized request/parameter and allowed read/write actions; use a lab, preserve request baseline and bounded evidence, and do not interpret a banner as permission to enumerate/exfiltrate data. Wireshark: capture only the allowed interface/filter/window, restrict retention/access and inspect actual protocol boundaries; decrypted captures can contain credentials. Official entry points: https://docs.metasploit.com/ ; https://github.com/sqlmapproject/sqlmap/wiki ; https://www.wireshark.org/docs/ . These playbooks are not fabricated live adapters.

## Fuzz campaign

Choose mutation from a meaningful seed corpus or generation from a grammar/structure. White/gray/black-box describe available feedback/knowledge, not a rule that all fuzz input is random. State valid/malformed input bounds, assertions/properties, sanitizer/failure monitor, reset, wall/CPU/memory budget and expected rejection semantics. Preserve minimized unexpected crashes, reproduction command, build/seed/version and regression; a parser returning its defined validation error is not a crash.

`sui-testing/scripts/fuzz_lab.py` runs a bounded seeded local frame-parser lab, with replay support; `assets/python-lab` adds a Hypothesis roundtrip property. For a native target, expose a small deterministic bytes-to-parser function, reset cross-input state and avoid unbounded IO. A libFuzzer harness implements the tool's input function and is built with supported compiler/coverage/sanitizer flags; replay the same artifact against the same build. AFL/AFL++ uses its supported instrumentation plus seed/output corpus and timeout/memory controls. AddressSanitizer detects particular memory errors during execution; it is neither a fuzz engine nor a universal detector. OSS-Fuzz is integration/service infrastructure and requires its project/build/harness/onboarding workflow.

Honggfuzz provides another feedback-driven native campaign; inspect platform/instrumentation/runtime flags and preserve its crash/reproducer artifacts. Syzkaller targets kernels and needs isolated supported VMs/kernel configurations, not an ordinary application test command on the user's machine. Radamsa mutates input; pair it with a bounded resettable target and explicit failure oracle rather than treating generated bytes as evidence a bug exists. Primary sources: https://llvm.org/docs/LibFuzzer.html ; https://aflplus.plus/docs/ ; https://github.com/google/honggfuzz ; https://github.com/google/syzkaller ; https://gitlab.com/akihe/radamsa ; https://google.github.io/oss-fuzz/ .

Hypothesis is property-based testing with generated examples and shrinking; specify a real invariant and preserve its reproducibility/version settings. BooFuzz targets structured protocol exchanges and needs a disposable authorized service, reset/failure monitor and result/replay handling (https://boofuzz.readthedocs.io/en/stable/). `python-afl` is a specific instrumentation integration whose runtime/support must be checked, not a synonym for every Python fuzzer. A generic PyFuzzer label does not uniquely establish a package: resolve the exact upstream/version/license before installation, otherwise use the verified local property lab and record the ambiguity. Do not install a similarly named package on resemblance alone.

## Result handling

Use Sui Implementation's strict supported report formats for Nmap/ZAP/SARIF and inspect raw sensitive evidence locally only as needed. Native fuzz crash logs require sanitizer/engine-specific triage and reproducibility, not the static compiler parser. Store a benign sanitized fixture for clean, finding, incomplete, malformed and failed-run outputs before claiming a new adapter. Separate configured procedure, fixture-tested parsing, observed native run and live target verification in the capability record. Missing account/tool/target prerequisites remain explicit; they are never silently promoted to passed.
