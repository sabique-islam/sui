# Performance, reliability and controlled failure experiments

Define user-visible hypotheses, not generic load charts.

For performance define workload mix, arrival/concurrency model, data size, warmup/cache, environment/versions, duration and p50/p95/p99/error/saturation metrics. Expected-load tests ask whether a requirement holds under representative use; stress tests go beyond design bounds to observe failure/recovery, not to produce a flattering throughput number. A soak test inspects sustained effects such as resource growth. State stop criteria, cleanup and owner before execution and collect the signals needed to detect the hypothesized bottleneck.

Use `scripts/load_probe.py --demo --requests 20 --concurrency 2 --execute` for a bounded loopback demonstration. For a reviewed target use `--url`, explicit request/concurrency/timeout/thresholds and `--execute`; remote hosts require an explicit exact allow-host within the user's authorization. Preview is default. Redirects are not followed, bodies are not retained and the probe records client latency/errors/throughput. Saturation is explicitly not collected; correlate target CPU/queue/lock/IO metrics before explaining a bottleneck. An overload fixture on a local demo is not a production capacity estimate.

For reliability distinguish a request good/eligible SLI from probability of failure-free operation over a defined time/environment. Time-to-failure/survival inference needs exposure, failure/repair policy, censoring and stated model; error-budget arithmetic alone does not supply it. Use representative profiles and record no-data/no-failure limitations.

For chaos define a steady-state user outcome, one fault hypothesis, smallest relevant target, blast radius, duration, monitor, abort condition and recovery action. Examples are an isolated dependency timeout or a disposable worker restart with an idempotent message. First verify the monitor can see the injected failure and that recovery restores invariants. Do not inject production faults or destructive writes merely because an example mentions Netflix. Redundant copies can share a software fault; test the failure mechanism rather than equating replica count with safety.

During an incident mitigate actual user impact with authorized reversible actions, preserve a redacted timeline, distinguish symptom/cause and confirm recovery. Afterwards identify contributing conditions and detection gaps without blaming a person, assign bounded follow-ups and verify the fixes. DevOps culture supports shared goals, empathy about downstream constraints, clear handoffs and scaling ownership; a tool installation alone does not remove a queue or resolve conflicting incentives. Improve one observed cross-functional handoff and compare whole-flow outcome plus safety guardrails.
