# Static analysis selection, execution and triage

Select from the actual language/build and risk. Do not install every named tool, and do not describe a vendor logo as an analyzer.

## Scope and proof levels

Inventory project language/runtime, compiler/build, manifests/lockfiles, existing checks/configuration, excluded/generated/vendor files and target changes. Choose fast compiler/type/lint checks plus a deeper analyzer when the actual failure mechanism warrants it. Record analyzer/version, flags/config, code/build identity, analyzed scope, suppressions and report. Pattern rules, type systems and data-flow/abstract interpretation have different approximation, cost and false-positive/negative boundaries; neither a clean scan nor compilation proves correctness. Dynamic tests remain complementary.

`scripts/tool_checks.py run --tool mypy --root /project --scope src/example.py` previews an argv command; add `--execute` for a reviewed authorized check. Native adapters are mypy, standalone TypeScript, GCC syntax/warnings and Clang-Tidy with an explicit local compilation database. Missing tools, failed version probes, timeout/output overflow, invalid reports and persistent input changes cannot be marked passed. Direct TypeScript mode uses explicit files/strict defaults; prefer the repository's configured `tsc -p ...` command for project-level evidence and import/inspect its output. An arbitrary argv runner is not an analyzer integration.

Use `tool_checks.py parse --format FORMAT --report FILE --completed --return-code N --root /project --scope SOURCE...` for supported supplied reports. That is normalization of an operator-supplied completed-run report, not independent execution/authentication or retrospective binding of its source. Default output hashes messages rather than printing potentially sensitive diagnostics; inspect relevant raw output locally with scoped redaction when diagnosing. `--include-messages` is an explicit disclosure choice, not a secret detector.

## Type, nullness and compiler examples

Mypy: inspect typed boundaries, Python target and imported stubs/packages; run the project configuration and preserve error codes/column locations. An `Any` dependency can hide errors; decide where stubs or strict boundary annotations are needed. A returned `str | None` must be checked before use; a `NewType`/unit wrapper can prevent mixing meters and milliseconds but cannot prove a runtime value is truthful. Review unused suppressions rather than widening `ignore_missing_imports` until green. Official flags: https://mypy.readthedocs.io/en/stable/command_line.html .

TypeScript: inspect `tsconfig`, strict-null behavior, module/runtime resolution and generated declarations. Run the configured compiler with no emit when checking only; pair type success with runtime validation of external JSON. Do not cast untrusted input to a desired type as proof it meets that type. Official CLI: https://www.typescriptlang.org/docs/handbook/compiler-options.html .

Checker Framework: choose the actual checker, JDK/build integration and annotation/stub policy; a nullness checker needs relevant library contracts and a fixture that rejects a nullable dereference. Unit/dependent annotations have specific expressiveness and assumptions. Integrate the version's processor through the native Java build, retain standard compiler diagnostics and test suppressed/generated/reflection boundaries separately. Official manual: https://checkerframework.org/manual/ .

Error Prone: integrate the installed plugin with the supported JDK/build tool and run an actual compilation containing a known bad pattern, then its repair. Use compiler diagnostics and rule IDs; inspect the current JDK requirement instead of copying an old javac invocation. Official: https://errorprone.info/docs/installation .

Clang-Tidy: produce the actual build's `compile_commands.json`, choose checks/header scope in a reviewed `.clang-tidy`, run with the compilation-database directory and inspect source-level diagnostics/exported fixes. The bundled runner accepts `--build-dir` and does not apply fixes. Validate macros/generated headers and suppressions; an irrelevant compile configuration can hide the real bug. Official: https://clang.llvm.org/extra/clang-tidy/ . C++ Core Guidelines is a check family shown in the source screenshot, not a separate analyzer.

## Deeper and platform analyzers

SpotBugs: compile matching Java bytecode, include the relevant auxiliary classpath, select intended filters/effort and export XML. A `BugCollection` with missing classes/analysis errors is incomplete; the parser rejects it. Validate a known null-dereference fixture and its repaired form. FindBugs is a historical predecessor. Preserve an existing supported setup and compare issue and config behavior before a deliberate migration rather than installing obsolete binaries because an old name appears in a list. Official SpotBugs CLI: https://spotbugs.readthedocs.io/en/stable/running.html .

Infer: capture the real supported build, analyze with versioned settings, preserve `infer-out/report.json` and inspect bug type, qualifier, file/line and trace. A standalone wrong build capture cannot establish project coverage. Verify a known bad/repaired fixture and library-model limits. Official worked build: https://fbinfer.com/docs/hello-world/ . The supplied-report adapter handles its documented issue-list subset.

SonarQube/SonarCloud: configure the exact project/source/test/exclusion paths and scanner/runtime for that product/edition, keep tokens in scoped secrets and obtain the matching analysis-task result. Scanner upload success alone is not the quality gate. Wait/poll the same task when the workflow requires a gate; preserve project/branch/revision and rule profile. Fetch all issue pages before normalization; the parser rejects an incomplete total. SonarCloud requires its own organization/project configuration and authorized source upload. Official: https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/scanners/sonarscanner and its versioned CI integration docs.

Snyk: choose SAST (`code test`) versus dependency/container/IaC scanning intentionally. For Code use its version's SARIF output; for dependency findings the local parser supports the `ok`/`vulnerabilities` JSON subset. Preserve exit semantics: an analysis failure or unsupported project is not a clean scan; a missing Code JSON output can be a documented no-findings behavior, so verify run status instead of assuming the missing file means clean. Source upload/network/account use needs actual task authorization. Official: https://docs.snyk.io/developer-tools/snyk-cli/commands/code-test and https://docs.snyk.io/developer-tools/snyk-cli/commands/test .

Coverity: inspect the licensed installed release, compiler capture/configuration, analysis directory, exclusions and completeness diagnostics. Export the exact supported JSON version or its documented SARIF conversion; do not parse v11 as v10. The shared SARIF adapter supports the converted SARIF subset, not every vendor-native field or account workflow. Current vendor documentation entry: https://docs.blackduck.com/ (search the release's `cov-format-errors`, JSON output and SARIF conversion). A vendor name on a report is not a second scanner to execute.

Squale is a quality-model aggregation platform (https://squale.org/introduction.html), not a universal command with a guessed JSON schema. For an existing deployment inspect version, underlying analyzers, quality model, metric units, data freshness and export API/schema; validate a sanitized real export before adding a parser. The pack provides the selection/migration procedure, not a fabricated native adapter. Keep that support tier explicit.

## Triage and baselines

For each finding reproduce the source/config path, inspect the rule contract, trace reachability/ownership and try to refute the failure. Distinguish confirmed defect, true-positive accepted risk, false positive, obsolete baseline and unknown. Do not discard a warning merely because it predates the diff; route it by risk while keeping unrelated work bounded. For a baseline store analyzer/rule/config/version and stable finding identity; report new versus existing findings without claiming existing debt is safe. A suppression needs rationale, owner, scope and expiry/revisit trigger. Do not hide diagnostics or change thresholds merely to make the gate green.

Use code examples from the task to inspect C memory/lifetime, command injection and mutable shared input ownership; test both denied/malformed behavior and legitimate caller compatibility. Reflection, generated code, dynamic loading and external state are explicit analysis limits. Do not attribute an analyzer from logo resemblance. Confirm the product from its own documentation, and do not carry forward an unverified PMD attribution.
